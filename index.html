CMS Scheduler

A permission-controlled way to prepare a task or question workflow action now and execute it at a chosen future date and time. Until that time, the mentor receives no assignment access and no assignment notification.

01 · Confirmed requirement

What the CMS Scheduler must do

A person with the new Scheduler permission can schedule an allowed CMS action for a future date and time. The action must not become a real mentor assignment before that time. Agenda.js executes it when it becomes due, and the existing CMS workflow performs the actual task activation/assignment or question review operation.

Create
Schedule the action now

Choose one existing operation, its target/mentor details and the future date/time.

Wait
No early side effects

No real assignment, mentor access or workflow notification is created before the due time.

Execute
Run the existing CMS flow

At or after the due time, validate and perform the normal CMS action, then notify its intended recipients.

Core design rule: the Scheduler stores an instruction for a future action. It does not create a second task or review workflow. At the scheduled time, it calls the existing workflow that already knows how to decide eligibility and update CMS records.

Three scheduled actions in two categories

The current scope covers only Exam Creation tasks, Question Creation tasks and Question Review. Tasks and Question Review are the two Scheduler categories. Other action types are future scope. The existing CMS publishing workflow remains separate from the Scheduler.

Scheduled action What happens at the scheduled time Notification timing
Exam Creation task Apply the task, set and section coordinator assignment plan, then activate the task using the existing task workflow. Only at execution: task coordinator, all applicable set coordinators and section coordinators.
Question Creation task Apply the task and set coordinator assignments, then activate the task using the existing task workflow. Only at execution: task coordinator and all applicable set coordinators.
Question Review Run the existing review eligibility and assignment flow. Only the version that is eligible under the current review rules should enter review. Only when the actual review assignment is created.
No new bulk-scheduling feature: the Scheduler creates one scheduled action for one normal CMS assignment/workflow operation at a time. It will not introduce a separate bulk-schedule builder, multi-schedule wizard or CSV scheduling flow. If an existing CMS action already supports selecting several questions as one review operation, the Scheduler can wrap that existing operation without adding a new bulk feature.
02 · Existing CMS foundation

Reuse the workflows already in Question Service

The Scheduler should sit in front of the current workflows. The scheduled record holds the future intent; the current controllers/services remain responsible for the actual domain changes.

Task creation and activation

Exam Creation and Question Creation tasks already have task, set and coordinator concepts. The Scheduler must hold the intended coordinator map separately and only write real assignments when the Agenda job executes.

Coordinator notifications

At due time, the existing task activation/assignment flow should notify the Task Coordinator, all assigned Set Coordinators and all assigned Section Coordinators. No task-assignment notification goes out when the schedule is first saved.

Question Review

Review already has eligibility and assignment logic. Do not create a parallel version picker in the Scheduler. At execution, call the existing review path; if a selected question is no longer eligible, skip/remove that question from this scheduled review and record why.

Existing integration points to preserve

Workflow Known current integration point Scheduler responsibility
Task creation controllers/task/task.controller.js → createTask Create and configure the task as a draft before scheduling; then create the schedule record. Do not make mentor assignments live.
Coordinator assignment Task controller coordinator assignment logic; Task.taskCoordinatorId, TaskSet.coordinatorIds, section coordinator data Persist intended coordinator IDs only in the schedule payload; apply them to the real Task/TaskSet/section records at due time.
Task activation Task controller activateTask and task.services.js Invoke existing activation after assignments are applied; rely on the normal task visibility/notification workflow.
Question review Direct question request-review and task-set reviewer assignment routes Call the existing review-eligibility/assignment path at due time. Retain the selected eligible version identity; skip changed question/version targets and never substitute another version.
Compatibility principle: “Schedule” should behave like “do the normal action later”. It should not fork or duplicate task activation, question review eligibility, access checks or notification templates.
03 · Solution design

Recommended architecture with Agenda.js

Use Agenda.js with its MongoDB backend as the durable delayed-job engine. Question Service still owns the Scheduler permission, the business record, the task edit lock, visibility rules and the action-specific execution logic.

Two MongoDB collections, two responsibilities: scheduledActions is the CMS business record used for ownership, permissions, display, task locking and audit. Agenda's agendaJobs collection is the internal execution queue. The CMS UI must read scheduledActions, not expose raw Agenda job documents.

Agenda's responsibility

Persist the delayed job, discover it when due, lock it for processing, coordinate concurrency and apply configured retry/backoff.

Question Service's responsibility

Check who may schedule/view/manage, lock the task, decide which existing business workflow to invoke, enforce idempotency and deliver normal CMS notifications.

04 · Complete flow

What happens before, at and after the scheduled time?

The browser only creates and manages the schedule. The backend worker executes it. The mentor is not assigned and notified until the Agenda job becomes due and the existing CMS workflow succeeds.

Time convention: the date and time chosen in the CMS are always interpreted and displayed in IST (Asia/Kolkata). The backend converts that IST time to a UTC execution instant for Agenda; the worker never uses the server machine timezone to decide when the action is due.

Never implement “hide it until later” as the only protection. Do not write reviewer IDs, Task Coordinator IDs, TaskSet coordinator IDs, Section Coordinator IDs, active task access or review records at schedule creation. Existing backend role checks or APIs could still expose a prematurely assigned record. Keep the real assignment state absent until execution.

Version rule for Review: Do not add a Scheduler-specific version selector or a separate version-selection algorithm. At schedule creation, retain the selected question ID, eligible version ID and a lightweight snapshot/fingerprint of the version that is currently eligible for review. At execution, run the existing CMS review eligibility logic. If the selected question/version has changed since it was scheduled, remove/skip that question from this scheduled review and record the reason. Do not silently substitute a newer/different version.

Future action types

Keep an action registry so more CMS operations can be added later. Every new action type must supply its own Scheduler permission mapping, existing workflow permission, target validation, execution handler and notification behaviour. Additional actions are outside the current scope and require separately confirmed requirements.

06 · Persistence and edit locking

What is stored, and how is a scheduled task locked?

Keep a CMS-owned ScheduledAction record for the business intent and let Agenda own its internal job record. For task assignments, a pending schedule must also lock the task from editing.

CONCEPTUAL DATA MODEL · BUSINESS RECORD, AGENDA JOB AND TASK LOCK
ScheduledAction · CMS-owned_id · actionType · status · scheduledAtUtc · timeZone · createdBy · projectId · action permission key · target IDs · intended recipients · agendaJobId · result · history[]
Agenda job · Agenda-ownedname: cms.execute-scheduled-action · data: scheduledActionId + scheduleRevision · nextRunAt · lockedAt · attempts / failure fields
Task lock · CMS-ownedTask.scheduleLock = { scheduledActionId, lockedBy, lockedAt }. Prevent edits to task, sets, sections and assignment configuration while active.
Existing domain recordsTask / TaskSet / Section · Question / Review · Users / Project. Actual assignee/reviewer state is written only when due.

Suggested ScheduledAction fields

Field group Purpose Notes
actionType Which existing CMS operation to run. Current categories: TASK_ASSIGNMENT (Exam Creation or Question Creation task) and QUESTION_REVIEW_ASSIGNMENT. No other action types are in scope.
scheduledAtUtc + timeZone Execution instant and fixed display timezone. All user-entered times are IST. Convert to UTC for execution and store timeZone: "Asia/Kolkata" for consistent IST display.
createdBy + projectId Creator ownership and project scope. Used to filter the creator's own scheduler rows and enforce owner/Admin controls.
payload Target IDs and intended action details. For task actions, store the intended coordinator map without applying it. For Review, store the selected question ID, eligible version ID and a lightweight fingerprint for change detection; existing CMS logic still decides eligibility.
agendaJobId + scheduleRevision Connect the CMS record to its Agenda job and reject stale jobs. Agenda job data should carry the schedule ID and expected revision, not a copy of the whole task/question.
status + executionResult CMS-facing lifecycle and result. SCHEDULING, SCHEDULED, PROCESSING, COMPLETED, PARTIAL, ACTION_REQUIRED, FAILED, CANCELLED.
history[] + idempotencyKey Audit actions and stop duplicate side effects. Record who created/cancelled/sent-now, when execution started/finished and the result.

Task edit lock behaviour

TASK EDIT LOCK · CANCEL FIRST, THEN EDIT
Schedule savedTask.scheduleLock points to ScheduledAction.
→
Task is lockedUI disabled + backend rejects task/set/section edits.
→
Cancel scheduleAgenda job cancelled; task lock cleared; normal edit permissions resume.
Important: showing a disabled Edit button is not sufficient. Every backend mutation endpoint that can change the scheduled task, its composition, sets, sections or coordinator mapping must reject the update while an active schedule lock exists. The user must cancel the schedule first; then edit and create a new schedule if required.

When does the lock clear? It clears when the creator/Admin cancels the pending schedule, or after the scheduled task assignment succeeds and the normal task activation commits. Once active, the task follows the CMS's normal post-activation edit rules. If execution ends in Action Required/Failed without activating the task, keep it locked until the schedule is cancelled so the task cannot be edited while a future action is still unresolved.

Consistency and indexing

  • Use indexes for Scheduler listing by createdBy, status, scheduledAtUtc, projectId and actionType, aligned to the actual query filters.
  • Prevent multiple active schedules from locking the same task unless product rules explicitly allow them. Use an atomic task lock claim.
  • Creating ScheduledAction, creating the Agenda job and locking the Task are multiple writes. Use a transaction where supported, or a recoverable SCHEDULING state and reconciliation path.
  • Keep audit/history even after cancellation. Do not delete a scheduled record merely because the user cancelled it.
  • No bulk-scheduling data model or batch scheduler API is required.
07 · Agenda execution engine

How Agenda knows the scheduled time has arrived

The browser is not involved after a schedule is saved. Agenda persists a one-time delayed job in MongoDB and processes it when due. Its handler reads the CMS ScheduledAction and executes the matching existing workflow.

AGENDA JOB LIFECYCLE · ONE SCHEDULED ACTION
1Save ScheduledActionBusiness status SCHEDULED, target payload and UTC due time.
→
2Agenda schedule()Create one job with ScheduledAction ID and revision.
→
3Wait until dueAgenda's backend discovers job when it is due.
→
4Lock & executeAgenda lock + CMS atomic state claim + existing workflow.
SCHEDULED→PROCESSING→COMPLETED

Runtime responsibilities

1
Define one stable job handler

For example cms.execute-scheduled-action. Its data contains only scheduledActionId and scheduleRevision; the handler loads the trusted payload from MongoDB.

2
Configure due-job polling

MongoBackend polls according to processEvery. Tune the interval against acceptable delay and MongoDB load. Agenda must never execute an action before its due instant.

3
Use Agenda locking and concurrency

Configure maxConcurrency, per-job concurrency, lock limit and lock lifetime. Also atomically claim ScheduledAction from SCHEDULED to PROCESSING so Cancel and Send Now cannot race with a running worker.

4
Retry only transient failures

Use bounded retry/backoff for temporary infrastructure failures. Invalid targets, changed review eligibility or permission conflicts should become an explicit skipped/action-required result, not retry forever.

5
Keep CMS audit and Agenda state aligned

Record execution started, completed, failure and retry information on ScheduledAction. Agenda owns its own lock and retry state; do not duplicate its lock mechanism in the CMS model.

6
Run as a managed backend worker

Start Agenda after MongoDB is ready and shut it down gracefully with the server. The browser never runs timers and the worker must recover jobs after restarts.

Send Now and Cancel

Cancel: atomically mark the CMS record CANCELLED, cancel the pending Agenda job and clear any task lock. Reject if the action has already entered PROCESSING.
Send Now: only the creator or Admin may trigger it. Move the pending job to immediate execution (or safely replace its pending Agenda job with a new revision), then use the same processor and validation path. Never call the domain workflow directly from the API and never create a second execution.

Timing contract: Agenda's MongoDB backend polls for due jobs. The configured processEvery, DB response and worker load affect how soon after the due time it starts. Define and monitor a practical delay SLA. Promise “not before scheduledAt”, not “exactly at the millisecond”.

Who can cancel or Send Now?

Do not receive access to a pending schedule and do not manage it from the Scheduler page.

Backend enforcement: on every list/detail/action API, derive identity and role from the authenticated server session. A non-Admin may operate only when createdBy === session.userId; an Admin may operate across creators. Never trust a frontend-provided creator ID.

Permission integration

  • Add a dedicated platform-level permission, suggested key scheduler, to the backend permission constants and frontend permission options / Users & Permissions UI.
  • Use the platform permission guard to show the tab, but also enforce login + Scheduler permission on every backend Scheduler endpoint.
  • At schedule creation, check the existing permission for the specific action type. Scheduler permission cannot grant Task Management or Question Review permissions.
  • Use creator ownership and Admin role for Cancel / Send Now. Do not allow another Scheduler-permission holder to manage a colleague's schedule.

10 · Time handling

All Scheduler dates and times use IST

What the user selects

A date/time picker that always uses Indian Standard Time (IST), for example 30 November 2026 · 10:00 AM IST. Do not use the browser or device timezone.

What the backend stores

An absolute UTC timestamp plus the fixed IANA timezone Asia/Kolkata. This is an implementation representation of IST, not a user-selectable timezone.

  • Reject dates in the past, including a time earlier than the current time on the selected day.
  • Send an unambiguous ISO 8601 instant derived from IST. Never send a timezone-free date string or interpret a browser-local timestamp as IST.
  • Store scheduledAtUtc and the fixed timeZone: "Asia/Kolkata". Agenda compares UTC instants only; the UI displays every schedule in IST regardless of the user's device timezone or the server's local timezone.
  • Once saved, the schedule time is not edited in-place in the Scheduler page. To change it, the creator or Admin cancels the current schedule and creates a new one from the source CMS workflow.
  • Agenda's polling interval determines how soon after the due instant the job starts. The system must never intentionally execute early; exact millisecond execution is not promised.
Example: the manager chooses 30 November 2026, 10:00 AM IST. The frontend interprets it in Asia/Kolkata (UTC+05:30) and converts it to 04:30 AM UTC. MongoDB stores the UTC instant with the fixed timezone metadata. Agenda executes at or shortly after that instant; every Scheduler screen displays 10:00 AM IST.
11 · Safety and edge cases

What if something changes before or during execution?

Agenda guarantees durable job processing, but the CMS must re-check its own business rules at execution time. The scheduled intent may become invalid while it is waiting.

Scenario Required behaviour Result
Task has an active scheduled assignment Block edits to task, sets, sections and coordinator mapping in both UI and backend. User must Cancel first to unlock. Locked
Creator cancels before due Atomically mark CANCELLED, cancel pending Agenda job and release Task.scheduleLock. Cancelled
Someone attempts to edit a locked task by API Reject in backend even if the frontend edit control was bypassed. Forbidden / Conflict
Mentor is inactive or no longer eligible Do not assign to that mentor. Record the affected recipient and tell the schedule creator/Admin. Action Required
Question/version changed before scheduled Review Remove/skip that question from this scheduled review if its scheduled target/fingerprint no longer matches. Do not switch to another version; record the skip reason. Skipped
Question review already exists Use existing conflict checks; do not create a second review. Record the reason. Action Required
Backend restarts before due time Agenda reloads the persisted job from MongoDB after startup; the CMS ScheduledAction remains the business record. Still Scheduled
Worker crashes after a side effect Agenda lock/retry handles job recovery; CMS idempotency key prevents duplicate assignments, reviews or notifications. Retry / Attention
